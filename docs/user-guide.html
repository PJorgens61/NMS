NMS — User Guide

A menu bar utility that watches your Mac's network path — router, ISP edge, DNS, HTTP, and any switches/APs you point it at — and tells you what actually broke.

1 Install & authorize

NMS is a single unsigned .app — no installer, no account, no configuration file. Everything it shows comes from reading your Mac's own network state directly.

1 Move it somewhere permanent

Drag NMS.app into /Applications (or anywhere you like — it has no installer and writes nothing outside its own sandboxed app-support folder). Running it from a Downloads folder works too, it just won't survive a cleanup pass.

2 Get past Gatekeeper

NMS is built and signed locally by its developer, not notarized by Apple — so the first launch will be blocked. Double-clicking it gives you a dead end ("Apple could not verify…" with no Open option). Do this instead:

  • Control-click (or right-click) NMS.app → Open → confirm Open in the dialog that appears, or
  • If that doesn't offer an Open option on your macOS version: System Settings → Privacy & Security, scroll to the Security section, and click Open Anyway next to the NMS mention — then launch it again and confirm.

You only do this once. After the first successful launch, it opens normally from then on.

3 Grant Local Network access

Almost immediately after launch, macOS will ask: "NMS would like to find and connect to devices on your local network." Click Allow. This is required — without it, NMS can only reach as far as your router, and SNMP/LAN device discovery return nothing.

4 Location access — only if you use Wi-Fi

macOS treats a Wi-Fi network's name (SSID) as location-sensitive, so reading it requires Location permission. NMS only asks the moment it's actually needed — the first time you're connected over Wi-Fi rather than Ethernet. Click Allow if you want the network name shown; if you decline, NMS keeps working, it just shows "Wi-Fi" instead of the network's name.

Optional — launch at login

NMS has no built-in login-item setting. To have it start automatically: System Settings → General → Login Items & Extensions, then add NMS under "Open at Login."

What it needs, and doesn't

No account, no cloud service, no phone-home. Local Network and (optionally) Location are the only two permissions it asks for, both explained above — everything NMS displays is read directly from this Mac.

2 The menu bar icon

One glance at the icon tells you whether anything needs your attention — click it to open the popover, click anywhere else to close it.

Green — normal

Everything on the critical path (router, ISP edge, internet, DNS, HTTP, public IP) is reachable.

Yellow — marginal

The critical path is fine, but something you're separately watching — an SNMP-monitored switch or AP — isn't answering.

Red — critical

Your network interface is down, or one of the critical-path checks is failing. Something is actually broken.

This is a strict priority order, not a count — one critical failure means red even if everything else is fine, and a marginal issue never escalates to red on its own.

3 Anatomy of the popover

Every section below is annotated against the same real capture, taken on a healthy home network. The popover is arranged as two side-by-side tiles up top (Network Health / Info, then Path to Internet / Speed Test), followed by three full-width lists (DHCP History, Events, SNMP Devices).

Network Health

Seven rows, each a colored dot plus a sparkline and a response time or status. They're deliberately ordered bottom to top as the actual path out of your Mac — read it that way when something's wrong:

Row (bottom→top)What it actually checks
NetworkIs there an active interface at all, and do we know what it's connected to (Ethernet, or a named Wi-Fi network)
Local RouterPing to your gateway's LAN address — is anything answering one hop away
Public IPPing to your own router's WAN-facing address — tests whether the gateway's internet-facing side is alive (catches a dead modem/ONT that the LAN-side check above can't see)
ISP Edge RouterPing to whichever traceroute hop you've confirmed as your ISP's own router (see Path to Internet below) — "Not confirmed" until you do
Internet Ping by addressPing to a fixed public address (1.1.1.1) — real reachability past your ISP, bypassing DNS entirely
DNSA fresh, cache-busting name resolution — catches DNS-specific outages that a raw ping wouldn't
HTTPAn actual HTTPS fetch — catches a captive portal or an ISP that filters everything but web traffic

Next to each row's response time is a small sparkline — its last ~30 checks, roughly the past 15 minutes. Successful checks draw a line; each layer scales its own line independently, since DNS's single-digit milliseconds and a real internet ping's tens of milliseconds would otherwise share an axis and flatten the faster one into a flat scribble. A failed check breaks the line rather than smoothing across the gap, and is marked with a small red dot along the bottom — so a bad patch is visible at a glance instead of silently averaged away.

Root cause vs. consequence

When several rows fail together, only the lowest one shows full-intensity red — everything failing above it shows a dimmed red, since it's presumed to be a consequence, not a separate problem. An asterisk (*) next to a failure means it started right around a network change NMS also observed.

Here's a real example — an upstream switch port was disabled, cutting this Mac off from everything past its own desktop switch. Local Router reads full red (the actual break), with its sparkline showing red dots at the moment it dropped; DNS above it is a dimmed red, since it depends on the router and is a consequence, not an independent fault; Network stays green throughout, because the Ethernet interface itself never went down — only the path behind it did:

That single detail — Network stayed green while everything below it went red — is itself a diagnosis: the fault is downstream of this Mac's own interface, not the interface or Wi-Fi itself. Once the fault clears, every row returns to green and Events records the whole episode as matching "became unreachable" / "reachable again" pairs — visible in the Events list of the full-popover capture above, from a real one-second network blip earlier the same day. See Scenario B for the general reading technique.

Info

Static context about the current connection: network name and type, IP address in CIDR notation, router and DNS server addresses, and your current public IP. On Wi-Fi, a BSSID row also appears with the specific access point's hardware address — useful on a network with more than one AP, to tell which one you're actually associated with. The Known network / New network line with a "seen N×" count tracks how often NMS has recognized this specific router before (by its hardware address) — useful for confirming you're actually back on your usual network, not a similarly-named neighbor.

Path to Internet

NMS traces the route out to the internet and asks you to confirm which hop is genuinely your ISP's own router, since the first non-local hop isn't always right — a campus or enterprise network can hand out its own public address space before traffic ever reaches the actual ISP. Tap the star (★) next to the correct hop to confirm it; that address is then pinged directly on the same fast cadence as everything else in Network Health, not re-traced from scratch each time. Trace Now, in this tile's own header, re-runs the trace on demand.

Speed Test

Sits beside Path to Internet as the tile grid's fourth entry. Run Speed Test measures download and upload throughput against a public endpoint — roughly 50MB of real data transfer each run, so it's a manual action, never run automatically in the background. Every run is kept, newest first, as a genuine time series rather than a change log — unlike DHCP History below, a run gets a row even when the numbers are close to the last one.

DHCP History

Every time your DHCP lease actually changes — a different server, a different assigned address, or different lease timing — NMS records it here, newest first. The newest entry doubles as "your current lease"; there's no separate current-lease display. Each entry is two lines: the server and assigned address (with the timestamp) on the first, and every other field the lease carries — broadcast address, gateway, DNS servers, search domain, lease/T1/T2 timers, and the DHCP transaction ID — on the second. Hover the second line for a short explanation of T1/T2 and the transaction ID, the two genuinely opaque parts of that line.

Events

A running log of state transitions only — not a stream of every check. An outage produces one red line when it starts and one green line when it clears; nothing is logged while things stay the same in either direction, healthy or not. A fresh install with a healthy network correctly shows nothing here yet, not an error.

SNMP Devices

Any switch, access point, or other SNMP-capable device NMS can reach gets listed with its name, current uptime, and software/firmware descriptor — a device that unexpectedly restarts (uptime resets) or changes descriptor (a firmware update) logs an event automatically. Each row's leading dot is that device's live reachability, from the same fast ping cadence Network Health uses — hover it for what gray/green/red mean here specifically. Scan clears the list and re-sweeps the subnet from scratch — expect it to take up to 15-20 seconds on a full /24.

Two devices sharing one physical network interface (a common VRRP setup — a pair of access points sharing a floating address) are shown as a single entry with both addresses listed, rather than as two separate devices.

SNMP community strings — the read-only "password" your gear expects — default to public. Click Change to edit them as a comma-separated list, tried in the order you list them; put whichever one your gear actually uses first, since every string ahead of the right one costs a real timeout on every silent device.

Footer controls

Refresh re-reads network state, public IP, and Wi-Fi network immediately rather than waiting for the next scheduled round. The camera icon next to it saves a screenshot of the popover to ~/Library/Logs/NMS/screenshots/ and logs an Events entry naming the file — meant for handing off a "here's what NMS is showing me right now" report without a separate manual capture step. Quit exits NMS. The small gray line under these three, when present, names the exact build running (a git commit, with a trailing + if it has uncommitted changes) — useful mostly for a build you're actively iterating on.

4 Usage scenarios

Scenario A — First time on a new network

1 Open the popover and check Info

Confirm the router/DNS addresses and public IP look right for where you are.

2 Confirm your ISP edge hop

Under Path to Internet, star the hop that's genuinely your ISP's router (usually the first non-local address, but check the hostname). This is what turns "ISP Edge Router" in Network Health from "Not confirmed" into a real, monitored check.

3 Sweep for local infrastructure (optional)

If you manage the switches/APs here, set the right community string and click Scan. Anything that answers gets tracked for restarts and firmware changes from then on.

Scenario B — "Is it my Wi-Fi, or is the whole internet down?"

Read Network Health bottom to top and find the lowest row that's failing — that's almost always the real fault, not the highest one:

  • Network is red: the interface itself is down — a cable, a Wi-Fi drop, or the adapter. Nothing past it can be evaluated.
  • Network is green, Local Router is red: your Mac is fine, but nothing beyond it answers — a switch, AP, or the router itself is the problem (this is exactly the outage pictured above).
  • Local Router is green, ISP Edge Router or Internet is red: your LAN is healthy; the break is upstream, between you and your ISP.
  • Everything below is green, only DNS or HTTP is red: raw connectivity works — this is a resolver or web-filtering problem specifically, not a real outage.

Each row's sparkline is worth a glance too — a run of red dots pinpoints exactly when a layer started failing, which is often the fastest way to tell "this just happened" from "this has been marginal for a while."

Scenario C — The suggested ISP hop looks wrong

On a campus or enterprise network, the first non-local traceroute hop can be your own organization's router, not the actual ISP. If the suggested hop's hostname doesn't look like an ISP (e.g. an internal-sounding name rather than something like bng3.snfcca05.sonic.net), scroll the hop list and star the correct one further down instead — Network Health switches to monitoring that address immediately.

Scenario D — Watching a specific switch or AP

Set the community string it actually uses, click Scan once to find it, and from then on NMS re-polls it every minute. Two things worth watching for in the SNMP Devices list: an uptime that resets to zero (an unplanned restart) and a software descriptor that changes (a firmware upgrade) — both generate an Events entry the moment they're noticed.

Scenario E — Recognizing you're on a different network

The Info section's "Known network" / "New network" line is keyed on the router's own hardware address, not its name — so it correctly tells apart your home network from a visually-similar guest network on the same router, and correctly recognizes your own network again after leaving and coming back, even across an interface change (Ethernet to Wi-Fi).

6 Troubleshooting

snmpget unavailable on this macOS version
Apple removed the underlying command-line tool. Nothing to fix on your end — SNMP features are unavailable on this Mac.
No SNMP devices found
Either nothing on your subnet answers SNMP under the current community string(s), or it's mid-scan (15-20s on a full /24) — check the string under Change first.
Network name never appears on Wi-Fi
Location permission was declined. Grant it under System Settings → Privacy & Security → Location Services if you want the SSID shown; NMS otherwise works fine without it.
Public IP shows "Not checked" briefly after launch
Normal — it resolves within a second or two of opening the app, not a fault.
App won't open at all, no dialog
Revisit step 2 in Install & authorize — this is Gatekeeper blocking an unnotarized app, not a crash.
Network Health flashed red briefly, but nothing appeared in Events
By design, not a bug. If every path-critical row (Router, Public IP, ISP Edge Router, Internet) fails at once while DNS or HTTP still succeeds, NMS treats that as this Mac being too busy to run its own ping checks on time — not a real outage — and skips logging it. The measurements are still recorded, so the sparkline may briefly show it; this is most likely to happen during something CPU-heavy running at the same time, like a build.

7 What it deliberately won't do

  • No push notifications, email, or remote alerting — it's a menu bar indicator you have to glance at, not a monitoring service.
  • Watches from this one Mac's point of view only — it can't tell you whether a problem is local to this machine or affects the whole network.
  • Sparklines cover roughly the last 30 checks per layer (about 15 minutes at the normal cadence) — a short-term trend, not a long-term historical dashboard with adjustable time ranges. Events remains a recent-activity transitions log, not a trend graph.
  • SNMP discovery covers the reachable local subnet only, not routed/remote segments.
NMS is a personal macOS utility, not a commercial product — this guide reflects the build noted at the top of the page.
